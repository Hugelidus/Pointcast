# Next.js App Router: what the code pointer says (2026-09-28)

**Question.** Next.js (App Router, React 19, Turbopack dev) is the most common stack among early users. React 19 removed `_debugSource`, and Server Components have no client fiber. What does Pointcast actually put in the spec there, and how much of it is right?

**Answer.** Before this change: nothing right. Of 13 elements, 6 got a code pointer to a Next.js build chunk (`used at: _next/static/chunks/14ei_next_0os_t-p._.js`), a wrong answer, and 7 got none, with `SegmentViewNode`, a Next.js internal, as their component. After it: all 13 chains match the ground truth, Server Components included; through the CLI or MCP server, 10 of the 11 elements whose text is written in the code get the right `text at:`/`data at:` line (the eleventh gets the right entry, one line off), and the 2 computed values stay silent. No wrong location.

## Setup

- **App**: [`dev/examples/next-dashboard`](../../dev/examples/next-dashboard/SCENARIOS.md), written for this: Next.js 16.3.6, React 19.3, `next dev --turbopack`, the default `create-next-app` layout (no `src/`, `@/*` → `./*`). Server Components (root layout, sidebar shell, three pages, a shared `StatCard`, shadcn-style `Button` and `Card` used from the server), Client Components (`NavLink`, Radix Tabs with state, a filter and a form with state), data in `lib/nav.ts` and `lib/data.ts`.
- **Ground truth**: the table in its [SCENARIOS.md](../../dev/examples/next-dashboard/SCENARIOS.md), written before any recording.
- **Recording**: `node dev/eval/typed/record.mjs --tasks-file dev/eval/typed/next-tasks.json --out <dir>`: the e2e build of the extension, headless Chromium, muted, typed mode, one Alt+click and one note per element, handoff off, downloads into a temporary folder.
- **Rendering**: `pointcast process <session> --repo dev/examples/next-dashboard --stdout --no-copy`, the local-repo route the CLI and the MCP server use. The extension's own clipboard copy is listed separately below.
- **Before**: the 0.6.0 code (`e8bef98`). **After**: this change.

### The extension's own clipboard copy

The chains above are captured by the extension and are in the pasted spec too. The `text at:`/`data at:` lines are not: at Stop the extension reads source from the page's dev server, and only Vite serves it (D9, route 3). The popup says so: *dev server source not available (not a Vite dev server)*. On Next.js, those lines come from the CLI and the MCP server, which read the local repo.

## What changed

Details and reasons in [D9, note 2026-09-28 (Next.js)](../decisions.md#d9-source-mapping).

- **Owner stacks mapped through Next's own dev source maps.** The call site of each element and owner is taken by React's own rule (the frame after the JSX runtime's), and mapped through the chunk's `.map` (client) or the dev server's `/__nextjs_source-map` (Server Components, whose owners React 19 hands to the client as `ReactComponentInfo`). Done in the page's MAIN world, asynchronously after the gesture; only project-relative paths and lines leave the page. A frame that cannot be mapped ends the chain.
- **`renderedBy: []`** for a page's or layout's own markup: the element's own line is its chain.
- **Resolver**: text rendered from a data module a Server Component imports (rule 5); `@/` through `tsconfig.json`'s `paths` when there is no `src/`; Next's `metadata` export is not on screen. Each is silent when ambiguous.
- **Checked unchanged**: Stage 0's 15 lookups on the three evaluation apps, resolved with the old and the new code against the apps' source: 15/15 identical (11 locations, 4 silent). All unit tests and code-pointer snapshots pass.

## What stays silent, and why

- **Computed text** (#7, #12): `formatValue(48210)` and `Showing: {status}` are not written anywhere. A guess (the number `48210` in `lib/data.ts`) would be right here and wrong elsewhere.
- **The same literal twice** in the searched files, as before.
- **`next dev --webpack`** (not measured): its client frames are `webpack-internal:///…` modules, which this change does not map, and its source map sources are `webpack://…` paths, which it does not name. By construction those elements get at most the component's name and no chain: silence, not a wrong path.
- **A custom `distDir`, or code outside the folder holding `.next/`** (another package of a monorepo): the project root cannot be vouched for, so those frames are not named and the chain stops there.
- **The extension's clipboard copy** has no `text at:` on Next.js (above).

## Limits of this check

One small app, written for the check, and one Next.js version (16.3.6, Turbopack). The chains follow Next's documented dev source maps; a Next.js release that changes the fake Server Component URLs or the map endpoint would make the chains stop (silence), not point elsewhere. No agent was run on these specs: this checks what the spec says, not what an agent does with it.
