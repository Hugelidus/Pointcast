# Evaluation on three real apps (2026-09-27)

**Question.** On real codebases, where finding an element means searching many files, does a coding agent find the right elements more reliably, faster or with fewer tokens when it gets a pointcast spec instead of text? And which of pointcast's two formats, `classic` or `requests`, should be the default?

**Short answer.** Pointing helps accuracy against the same words without pointing (89 % vs 78 %), but a careful written description is still better (96 %) and uses about a third fewer tokens. pointcast does **not** save tokens. Between the two formats, `requests` is more accurate than `classic` (89 % vs 84 %) with 27 % fewer input tokens, fewer turns and 40 % less time, so it is now the default.

## Setup

- **Apps** (harness: [eval/README.md](../../eval/README.md)): three open-source admin dashboards on Vite dev servers, each split into one component per file.
  - [shadcn-admin](https://github.com/satnaing/shadcn-admin) (React 19, TanStack Router, shadcn/ui)
  - [vuestic-admin](https://github.com/epicmaxco/vuestic-admin) (Vue 3, Vuestic UI)
  - [flowbite-svelte-admin-dashboard](https://github.com/themesberg/flowbite-svelte-admin-dashboard) (SvelteKit 2, Svelte 5, Flowbite Svelte)
- **Requests:** 5 changes per app, spoken in Spanish (synthesized narration, ~31–33 s), mostly with deictics ("este botón", "esta tarjeta") and one without. The apps contain the ambiguity pointing is meant to remove: two "Export" buttons, two identical "Users" cards, two "Sales Report" links, a shared `Button` component.
- **Recording:** the real extension (e2e build) in headless, muted Chromium, with the narration as the microphone. The script Alt+clicked or selected each element at the start of its word; every gesture landed within 15 ms of its planned time. Whisper (`Xenova/whisper-base`, in the browser) transcribed each recording. All 15 gestures captured the intended element (checked by hand before any run).
- **Conditions** (the same task prompt, only the request differs):
  - **P-classic:** pointcast's `classic` spec (transcript with inline markers, plus an appendix per element).
  - **P-requests:** pointcast's `requests` spec (one request per sentence, with search hints per element).
  - **M1:** the same Whisper transcript, without the pointing.
  - **M2:** a careful written description naming visible labels, written from the screen only.
- **Agent under test:** `claude -p`, Sonnet, medium effort, tools Read, Grep and Glob only, isolated from user settings, plugins and MCP. Task: list every change with file, line and target; no editing.
- **Runs:** 3 apps × 4 conditions × 3 repeats = 36, 4 in parallel. All 36 returned a structured answer. Total cost: $3.42.
- **Grading:** deterministic, per change (`eval/grade.mjs`). A change is correct when at least one answer item addresses it and every item that does is the right element in an accepted file. Hedging between the right element and a wrong one, or editing a shared construct, is wrong. Every decision is in `grades.json`.

## Per-app notes

- **shadcn-admin.** Four of five changes were easy for everyone (a single `Download` button, a card with a unique title, the only chart, the `Chats` badge in the sidebar data). The fifth separated the conditions, and pointcast lost it: "el texto de ventas recientes, que diga últimas ventas del mes" meant the card's description, "You made 265 sales this month." The user selected it, but fusion placed the selection at the pause *before* the sentence ("…no hace falta, fuera *[e5]*. Y el texto de ventas recientes…"), so both P formats attached it to the previous request. Agents then either removed the description (reading it as part of "fuera") or renamed the "Recent Sales" title, or both. P got it right in 1 of 3 runs per format, the same as M1; M2, which quotes the text, in 3 of 3.
- **vuestic-admin.** Pointing clearly paid off. Without it (M1), agents took "esta tarjeta" to be the Yearly Breakup card in all 3 runs (the right one is Employees), and picked the Export button of the other card once. Both P formats got 15/15. `classic` needed 171 k tokens and 90 s per run against 97 k and 31 s for `requests`; the `requests` spec lists each element's component with its file (`LineChart` in `src/components/va-charts/chart-types/LineChart.vue`, `VaButton`, `VaBadge`), while the `classic` appendix does not show components at all, so the agent had to find them by searching.
- **flowbite-svelte-admin.** Pointing did not help on the hardest change: every P run (6 of 6) got the "Sales Report" link wrong. Two cards on the page have a link with that text (ChartWidget and CategorySalesReport), both rendered by the shared `More` component. The spec said `a «Sales Report»`, `component More in src/lib/More.svelte:18` and a path of `main › a`: nothing about *which card*. Agents went to other `More` usages ("Full Report", "Read more") or to the wrong card. M2 named the card ("$45,385 · Sales this week") and got it 3 of 3; M1 went to "Full Report" all 3 times. The duplicate "Users" card was found by every condition (M1 and M2 from "the second one"; P from the positional selector). One `classic` run placed three answers in `src/routes/(sidebar)/+page.svelte`, a 15-line file that only renders `<Dashboard />`, with line numbers from `Dashboard.svelte`.

## Typical failures

1. **The element is shared, and the spec does not say which instance.** pointcast reports the innermost component (`More`, `Button`, `P`) and a short path. When the same component renders the same text twice, the agent needs the surrounding card or its heading, which a person writing M2 naturally gives. (flowbite "Sales Report": 0/6 for P.)
2. **A selection anchored to the wrong sentence.** A selection made at the start of a sentence can be placed at the pause before it, so it lands in the previous request. (shadcn subtitle; in flowbite the "Sales this week" selection also went to the previous request, but the spoken words named the text, so no harm.)
3. **Without pointing, "this card" is a guess.** M1 removed the wrong card in 3 of 3 vuestic runs and picked the wrong Export once.
4. **Hedging.** Several wrong answers list the right element plus a second candidate (the other title, a data file). The grader counts these as wrong on purpose: an agent that edits both changes something the user did not ask for.

## Formats: why `requests` is now the default

| | P-classic | P-requests |
|---|---|---|
| Correct | 38/45 | 40/45 |
| Input tokens per run | 133.9 k | 97.3 k (−27 %) |
| Output tokens per run | 4.1 k | 2.5 k |
| Turns | 15.4 | 12.2 |
| Time | 50 s | 30 s |
| Spread of input tokens (std. dev.) | 61 k | 22 k |

`requests` is at least as accurate on every app and cheaper and faster on two of three (on shadcn-admin the two are equal within noise). The main difference seen in the answers is the per-element search hints, above all the component and its file, which only `requests` shows. Following the rule set before the run (accuracy first, then tokens and turns), `requests` is the default in core, so in the extension, the CLI and the MCP server. `pointcast process --format classic` still renders the old layout, which is better for checking a recording against its timeline.

## What this shows

- **Pointing removes the ambiguity of deictics.** Against the same words without pointing, pointcast (`requests`) got 5 more changes right out of 45, and the gain was where "this" had several candidates (vuestic: 15/15 vs 10/15).
- **A careful written request is still better, and cheaper.** M2 got 43/45 with 65 k tokens per run; pointcast got 40/45 with 97 k. The user still saves writing that description, which is pointcast's point, but on these apps it does not save the agent any work.
- **pointcast does not save tokens.** Its spec is only about 2 k characters (~500 tokens) longer than a written request; the difference is that the agent searched more. Token savings from pointing would need hints that land the agent directly on the file, such as source locations (`file:line` of the instance, not of the shared component).

## Changes made during this evaluation

- **Bug fixed: no text selection was ever recorded on SvelteKit apps.** SvelteKit wraps the app in `<div style="display: contents">`; Chrome's `checkVisibility()` is false for an element without a box, so pointcast treated every text on the page as hidden and dropped every selection. `isHidden` now treats a `display: contents` element as visible as its parent (`packages/extension/src/lib/text.ts`, with tests). All three apps were re-recorded with the fixed build.
- **Gesture plan:** the "Users" card is pointed at by its heading; pointing at its center hit the chart inside, whose random `apexcharts…` id says nothing about the card.
- **Grader tightened after a manual audit of every answer**, before computing the tables above: shadcn's subtitle no longer accepts an answer that only mentions "Recent Sales" (that is the card title, a different element), and flowbite's link only accepts `ChartWidget.svelte` and rejects the "Read more" link. Without these fixes, the grader had counted 8 wrong answers as right (3 per P format, 2 in M1, none in M2), and pointcast looked better than it is (P-requests 43/45).

## Limits (read before quoting)

- Three apps, five changes each, 3 runs per condition, one model and effort level: differences of one or two changes out of 45 are within noise. The shadcn subtitle and the flowbite link decide most of the gap between conditions.
- Synthesized narration and scripted gestures timed to the word: a real user points less precisely, and speaks less cleanly. Whisper still misheard words ("dasibode", "descargar CSU", "sales de Yswick"), identically in P and M1.
- M2 was written by the person who designed the scenarios, knowing which elements were ambiguous; a user in a hurry may write something closer to M1.
- Identification only: the agents did not implement the changes. Grading checks the element, not the action ("remove" vs "rename").
- Raw results, prompts and grades are in `eval/.runs/full-2026-09-27/` on the machine that ran them (not in git); `node eval/run.mjs` reproduces the run.

## Addendum (2026-09-27): after fixing the two typical failures

The first two failures above had a fix each, and both apps where they cost changes were recorded and run again:

- **The card around an element** ([D5 note](../decisions.md#d5-html--capture-generously-already-sanitized-render-lean)). Capture now records the title of the card or section around each element (`ElementInfo.context`), and the `requests` format shows it: the flowbite link is now `a «Sales Report» in «$45,385 · Sales this week»`, the words M2 used.
- **A gesture at the start of a sentence** ([D4 note](../decisions.md#d4-fusion--monotonic-alignment-of-events-to-deictic-words)). An unmatched event in the second half of a pause, or running into the next word, now goes with the words after the pause. The shadcn selection is now in its own request: "> Y [a] el texto de ventas recientes, que diga últimas ventas del mes." In flowbite, the "Sales this week" selection moved to its request too.

**Method.** Same harness and settings as above: shadcn-admin and flowbite-svelte-admin re-recorded with the new e2e build (every gesture again within 16 ms of its word, all on the intended element), then **P-requests only**, 3 runs per app (6 runs, $0.63), graded by the same `eval/grade.mjs` with the same ground truth. The earlier sessions are kept in `eval/.runs/full-2026-09-27/sessions/`, the new runs in `eval/.runs/followup-2026-09-27/` (not in git).

- **Where it is still wrong.** In one flowbite run the agent read "ver informe completo" as the existing "Full Report" link and edited that one, the same mistake M1 made in all three of its runs; the spec named the right card, but the words won. In another, the subtitle answer was right (`Dashboard.svelte:112`) but hedged with a second, low-confidence edit in an example route that repeats the same props (`ChartWidgetEx.svelte`); the grader counts hedging as wrong, as before. That change was 3/3 before, so it is noise or a side effect of a spec that now names the card; three runs cannot tell.
- **Tokens and cost do not clearly move.** shadcn used 16 % more input tokens, flowbite 19 % fewer; both cost a little more per run (more cache writes). With three runs per app, this is within the spread seen above.
- **Honest limits.** Six runs on the two apps the fixes were designed for, with the gestures of the same scenarios: this confirms that each fix does what it was built for on real data, not that pointcast now beats a careful written request. On both apps P-requests is now at or one change below M2 (28/30 against 29/30). vuestic-admin and the other conditions were not re-run.
- **Not solved: card titles that are not headings.** shadcn/ui's `CardTitle` is a `<div>`, so shadcn elements get their tab ("in «Overview tab»") rather than their card; MUI and Ant Design titles are `<span>`/`<div>` too. Reading those would need design-system-specific rules, left for later.
