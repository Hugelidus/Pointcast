# Typed mode, code pointer and MCP server on four apps (2026-09-28)

**Question.** With Pointcast 0.4 as a user gets it (typed notes, the code pointer resolved in the repo by the MCP server, Django template markers), how much does a coding agent save in tokens, tool calls, searches and time, and is it more accurate, against a realistic hand-typed request?

**Short answer.** On 16 single-element UI changes in four apps (5 runs each, 240 runs), the agent that read the recording through the pointcast MCP server (**C**) picked the right code in **77/80 runs (96 %)**, against **67/80 (84 %)** for a quick hand-typed request (**A**) and **75/80 (94 %)** for the Pointcast spec without code lines (**B**). It searched much less: **0.76 Grep/Glob per run against 1.89 for A (−60 %)**, and 55 of its 80 runs made no search at all (A: 0 of 80). It did **not** save tokens, time or money: median input 30.5 k tokens against 28.0 k for A (+9 %), the same median time (6 s) and about the same cost ($0.023 against $0.024 per run). On these one-change tasks the agent's fixed context (~18–28 k tokens) dwarfs the search it saves, and C pays one extra round trip (`get_session`) plus the MCP tool definitions. Every A error was a hedge: the agent's most confident item was always right, but it also listed a second place (a demo copy of the component, the other card) that it would have edited too.

Read [Limits](#limits-and-threats-to-validity) before quoting these numbers.

**Follow-up: batching** ([results-2026-09-28-batching.md](results-2026-09-28-batching.md)). The same harness, with sets of 6 changes per app delivered one by one, two by two or all six in one run. The token saving this page does not find for one change per request appears once changes are batched. With 6 changes in one recording, C used 58 k input tokens per set of 6 against 76 k for a hand-typed request with the same 6 changes (−24 %), cost 27 % less and searched 75 % less, at 96 % accuracy against 85 %. Against C one by one, the same set cost 73 % fewer tokens.

## What was compared

The same task prompt as every earlier evaluation (`dev/eval/prompt.md`: find where each change goes, reply with `file`, `line`, `target`, `confidence`; do not edit), with a different request inside:

| Variant | What the agent gets |
|---|---|
| **A** realistic hand-typed | A request of at most 40 words, written in Spanish by an independent `claude -p` writer (Sonnet) that saw only a screenshot of the page with the element outlined in red and one sentence of what the developer wants ("the outlined button should say «Descargar CSV»"). No source, no note, no spec, no ground truth. Like Stage 0's M3, but the writer saw the whole screen (card titles included), so it could be as precise as a person looking at the page. |
| **B** Pointcast without code | The spec of the same recording, rendered by the CLI from `session.json` with `renderedBy`, `resolved` and the component's file/line removed (a Django element's component, a template name, removed whole). What is left is the DOM description: the note, text, card context, path, styles, html, the framework component's name. |
| **C** Pointcast as a plugin user gets it | The recording itself, reached through the pointcast MCP server (`node packages/cli/dist/index.js mcp --repo <app> --dir <sessions> --no-handoff`), configured for that run only by `--mcp-config`. The request says only: get the latest session with `get_session`, follow its rules, and the plugin skill's step 4 (use `text at:`/`data at:` first, do not edit a shared component, search only without a pointer). `get_session` resolves the code locations in the app's source. |

## Method

- **Recordings: the real extension, typed mode, headless.** `dev/eval/typed/record.mjs` loads the e2e build (`chrome-mv3-e2e`) in headless Chromium (`--mute-audio`, profile and downloads in a temporary folder, checked before recording), sets the popup to Typed, Spanish, notifications off and **handoff off**, and per task: Record, one Alt+click (12 tasks) or text selection (4), types the note into Pointcast's note box, Enter, Stop. No microphone and no speech model. All 16 sessions captured exactly one event on the intended element (checked against the element's text before recording) with a real `renderedBy` chain (2–3 frames). The screenshot for A's writer is taken after Stop.
- **Specs.** `dev/eval/typed/prepare.mjs` renders B with the CLI and writes C's `--mcp-config` (one sessions folder per task, so `latest` is that recording). For the record it also saves what `get_session` returns (`get-session.preview.md`, rendered by the same resolver through `pointcast process --repo`). Every prompt was hashed before the first run (`prompts.sha256`, and `A/…/prompt.sha256`).
- **Agent under test.** `claude -p`, Sonnet (`claude-sonnet-5`), medium effort, CLI 2.1.258, tools Read, Grep and Glob only, `--setting-sources ""`, `--strict-mcp-config`, `--disable-slash-commands`, `--no-chrome`, `--no-session-persistence`, `--permission-mode dontAsk`, the answer schema of `dev/eval/run.mjs`, `--output-format stream-json --verbose` so every tool call is logged. C alone adds `--mcp-config` and the three pointcast tools.
  - **One deliberate difference from the earlier runs:** `--safe-mode` is off in all three variants, because it also disables MCP (checked: with it, C's run listed no pointcast tools). Auto memory was turned off with `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` instead (a first smoke test without it created an empty `memory` folder under `~/.claude/projects`, which was removed; no run after that created anything there). No CLAUDE.md exists in the apps or any folder above them.
- **Runs.** 16 tasks × 3 variants × 5 repeats = 240 runs, 4 at a time, below-normal priority, variants interleaved per task. All 240 returned a structured answer; none hit an error or the budget cap.
- **Grading.** `dev/eval/typed/grade.mjs` applies `dev/eval/grade.mjs`'s rules unchanged, one change per task: correct when every item of the answer is the right element in an accepted file. **Hedging counts as wrong**, as before: an agent that lists a second place would edit it. Tokens are uncached + cache write + cache read as the CLI reports them; time is the CLI's `duration_ms`; searches are Grep and Glob calls; "searches before the first truth read" counts them until the first Read of a ground-truth file. Tool calls include the final `StructuredOutput` call and, for C, the MCP calls.
- **Audit.** Every distinct answer (file, line, target, confidence) was read by hand after grading. One ground-truth expression was too loose and was tightened before these tables were computed: refund-amount accepted `39|jackson`, which also matched an item for **Sofia Davis's row, which shows the same +$39.00** (not noticed when the task was written). It now requires `jackson` at line 33. Before the fix, B had 78/80 and C 80/80; A was unaffected.

## Failures, one by one

**A (13 wrong, all hedges: the most confident item was right every time).**
- *stats-title, 0/5.* Every run answered `Dashboard.svelte:76` and also the demo copy `src/routes/api-check/dashboard/examples/StatsEx.svelte:44` (confidence 0.7), which holds the same `title: 'Statistics this month'`. A grep for the visible text finds both; nothing in the request tells them apart.
- *tablet-16k, 1/5.* The same with `TrafficEx.svelte:28` (confidence 0.3–0.6).
- *sales-report-link, 1/5.* Two cards show a «Sales Report» link. The writer's request placed it in "the statistics panel" (it is in the sales chart card), and 4 runs hedged between `ChartWidget.svelte:27` and `CategorySalesReport.svelte:41`, after 4–8 searches and up to 88 k tokens. Stage 0's M3 lost this link 0/3 too.

**B (5 wrong).**
- *refund-amount, 2/5.* Two rows show «+$39.00». The spec's DOM path (`div[role=tabpanel][2] › div[2]`) could tell them apart, but 3 runs hedged between Jackson Lee's and Sofia Davis's rows at 0.45–0.5 each.
- *ongoing-value, 1 run:* right line and construct (`value: '15'`, line 52) in the wrong file name (`Dashboard.vue` instead of `DataSection.vue`).
- *menu-projects, 1 run:* hedged `gb.json:57` with `NavigationRoutes.ts` (`displayName: 'menu.projects'`, 0.55).

**C (3 wrong, all refund-amount).** The same hedge between the two +$39.00 rows as B. Here the code pointer had nothing to add: the resolver stays silent because `+$39.00` is written twice in `recent-sales.tsx` (its rule: silence beats a wrong line), React 19 frames have no line, so `used at:` names only `<RecentSales>` in `index.tsx`. A, whose writer named "Jackson Lee", got it 5/5. Pointing is worth nothing here unless the spec says *which* instance, and the person who types it naturally does.

## What the product produced on real captures

The code locations the agent got in C (from `get-session.preview.md`):

- **Resolved to the exact line (10 of 16):** download-green, export-regions, ongoing-value, expense-label, tablet-16k, stats-title, sales-report-link, and on Django imprint-label, authors-count (`index.html:26`, the template line; the right edit is in the view), sidebar-genres (`base_generic.html:25`, through the `{{ block.super }}` of the book page's own block: the markers and the resolver handled the parent template correctly).
- **Chain only, no `text at:` (6):** overview-title («Overview» is written three times in `index.tsx`), refund-amount (written twice), status-bold (the text comes from `get_status_display`), since-new-products (four cards pass the same literal; `used at:` was the shared `Change.svelte:43`, and `within:` named `Dashboard.svelte:121`, which every run followed), users-nav and menu-projects (below).
- **users-nav (shadcn):** the real chain was `nav-group.tsx` ← `<Slot.Slot>` in `components/ui/sidebar.tsx` ← `<TooltipTrigger>` in `components/ui/tooltip.tsx`. The Radix wrapper frames used up the 3-frame cap, so the chain never reached `app-sidebar.tsx`, which imports `sidebar-data.ts`, and the spec had no `data at:`. Stage 0's hand-built chain for the Chats badge in the same sidebar did reach it. The agent still found `sidebar-data.ts:77` with one search in every run.
- **menu-projects (vuestic, i18n):** the label comes from `t('menu.projects')` in a locale file, which the resolver does not cover (D9, "Not covered"). C then cost the most of any cell (median 123 k tokens, 7 searches, 24 s): it read the spec, then searched like B.
- **Django:** at Stop the extension resolved nothing (not a Vite server, as designed), and `get_session` resolved all three literal texts in the repo. So on server-rendered apps the MCP route is the only one that gives `text at:`, which is what the README says.
- **A `find:` line with a `node_modules` path.** For flowbite-svelte's library components the spec says `component Span (svelte) in node_modules/.pnpm/flowbite-svelte@1.28.1_…/Span.svelte:27`. D9 says "defined in" never shows a node_modules path; the `find:` line still does. It misled no run, but it is noise and leaks a local layout.

## What this shows

- **Accuracy: yes, where the request is ambiguous for reasons the typist cannot see.** On *shared* and *data* tasks C was 35/35 and 35/35, A 22/35 and 26/35. A's losses came from things a person typing from the screen does not know about (a demo copy of the component, two links with the same text in two cards). B, the DOM description alone, got most of the same gain (35/35 and 33/35): the card context and the note carried it, the code lines added little accuracy on top.
- **Search: C removes most of it.** 0.76 Grep/Glob per run against 1.89 (A) and 2.31 (B); 55 of 80 C runs went straight to the file. Where the typed request was unambiguous and its text unique (9 of 16 tasks), A needed one grep, so there was little to save.
- **Tokens, time and cost: no saving on single changes.** Median input 30.5 k (C) against 28.0 k (A). C always pays one extra round trip for `get_session` and ~2 k tokens of MCP tool definitions, which, with a floor of ~18–28 k tokens of fixed context per run, cancels the one grep it saves. C was cheaper where A searched more (export-regions, download-green, users-nav, status-bold: about 7 k fewer tokens) and on the hard flowbite tasks where A hedged (sales-report-link: 31.5 k against 70.4 k), and dearer where A needed a single grep. Stage 0's −57 % came from sessions of 5 changes against Stage 0's own baseline; this evaluation does not reproduce a token saving for one change per request.
- **B vs C.** Same accuracy within noise (75 vs 77 of 80), with C making a third of B's searches and, on the flowbite data tasks, half of B's tokens (30 k against 53 k on tablet-16k and stats-title).

## Limits and threats to validity

- **Small and designed.** 16 tasks, 5 runs per cell, one model (Sonnet) at one effort. One task (refund-amount) decides most of the gap between B/C and A on shadcn; three flowbite tasks decide most of A's losses. Differences of 2–3 runs out of 80 are noise.
- **The tasks and the ground truth were written by the evaluator, who had read the source** (to write the ground truth) and knew the earlier evaluations. Three tasks repeat earlier traps (Download, the second Export, the Sales Report link). Two traps were not planted and were found only in the answers: the flowbite demo copies (they hurt A) and the duplicate +$39.00 (it hurt B and C).
- **Who wrote what.** The notes of B and C were written by the evaluator (short and deictic, as a note next to the element is). A was written by an LLM writer looking at a screenshot; one of 16 texts misplaced the element (sales-report-link) and one was vague in a way a person might also be. A first batch of writers, given the screenshot as a file, answered without opening it in 14 of 16 cases; that batch was discarded before any run (kept in `discarded-writers-v1/`) and the screenshot was then sent inside the message.
- **Single changes.** Real Pointcast recordings usually hold several changes; the fixed context per run then weighs less and the search saved per change adds up. That is the setting of Stage 0 and it was not re-run here.
- **C's request carries the plugin skill's guidance** (use `text at:` first, do not edit shared components); A and B do not get it. That is how a plugin user runs Pointcast, but it is a difference in instructions, not only in information.
- **`--safe-mode` was off** (see Method), unlike the earlier runs; auto memory was off instead. Absolute token counts are therefore not comparable with the 2026-09-27 tables.
- **Hedging is graded as wrong.** Counting only the most confident item, all three variants are at 79–80 of 80: the difference in accuracy is entirely about whether the agent adds a second, lower-confidence place.
- **Identification only.** No edit was applied; grading checks the element, not the change.
- **Django: one small app** (31 templates, no `{% include %}`). The partial case was tested only as a parent template's block shown through `{{ block.super }}`, not as an include; HTMX was not tested.
- **One recording per task, by a script:** the pointing is exact. A person's Alt+click can land on a wrapper or a sibling.
- The ground-truth fix after the audit (refund-amount) is disclosed above; no other expression was changed.
